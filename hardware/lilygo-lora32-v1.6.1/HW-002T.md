# HW-002T — responder timing instrumentation

HW-002T is a timing-instrumentation revision built on top of the physically
validated HW-002 measurement ping/pong.

Its purpose is narrow: explain the structured sub-millisecond variation seen in
same-bench HW-002 RTT results **without changing the H2 radio wire format**.

## Invariants

HW-002T deliberately keeps all of these unchanged:

- H2 magic and `HW2_VERSION=1`;
- H2 PING/PONG frame layout;
- deterministic probe bytes and CRC16;
- equal PING/PONG frame length;
- frozen PHY: 868.100 MHz, BW125, SF7, CR4/5, sync word `0x12`, 10 dBm,
  8-symbol preamble;
- autonomous responder behavior;
- initiator `MRESULT` semantics.

The new data is emitted only on the responder USB serial connection.

Boot capability is explicit:

```text
READY hw-002t
INFO ... lab=hw-002t measurement_ping=1 timing_trace=1 timing_trace_version=1
```

The ordinary `hw002.py` runner remains compatible with HW-002T because the H2
radio transaction and `MRESULT` shape are unchanged.

## Why two serial ports?

The original HW-002 host intentionally opened only the initiator serial port so
USB/Python could not affect the responder turnaround.

HW-002T opens both ports **for observation only**. The responder still receives
PING and transmits PONG entirely in firmware. Python does not command the
responder during the RF transaction.

```text
                 LoRa H2 PING
initiator  --------------------------> responder
    |                                      |
    |                                      | RX-done IRQ timestamp
    |                                      | handler entry
    |                                      | readData done
    |                                      | PONG prep
    |                                      | TX start / TX done
    |                 LoRa H2 PONG         |
    | <------------------------------------ |
    |                                      |
 MRESULT                              H2RESP + timing
    \______________________________________/
                 host correlates seq
```

## Responder timing trace

A successful H2 response now prints the existing fields plus timing detail:

```text
H2RESP seq=... bytes=... rssi_dbm=... snr_db=... toa_us=... state=0 \
  timing_v=1 \
  irq_to_handle_us=... \
  handle_to_read_done_us=... \
  read_done_to_tx_start_us=... \
  irq_to_tx_start_us=... \
  tx_block_us=... \
  irq_to_tx_done_us=...
```

Semantics:

- `irq_to_handle_us`: responder-local delay from SX1276 RX-done DIO0 callback
  to entry of `handleReceivedPacket()`; this captures loop/scheduling latency;
- `handle_to_read_done_us`: handler entry through RadioLib `readData()`
  completion;
- `read_done_to_tx_start_us`: RSSI/SNR read, H2 validation, PONG construction
  and time-on-air calculation before the TX call;
- `irq_to_tx_start_us`: sum of the three previous responder pre-TX intervals;
- `tx_block_us`: responder blocking transmit path, including standby/driver work
  and physical PONG transmission;
- `irq_to_tx_done_us`: responder RX-done IRQ to responder TX completion.

All intervals are measured on one ESP32 with unsigned `micros()` differences.
No absolute clock synchronization between the two boards is assumed.

## Diagnostic RTT decomposition

For a successful transaction with a matching responder trace the host derives:

```text
known_local_intervals
  = initiator_tx_block
  + responder_irq_to_tx_start
  + responder_tx_block

rtt_residual
  = initiator_rtt - known_local_intervals
```

The residual is **not propagation delay**. It still combines uninstrumented
radio/driver boundaries, independent-clock tolerance and propagation. Its value
is diagnostic only.

The main target is the directly measured responder-local
`irq_to_handle_us`: if the previously observed ~0.8–1 ms RTT phase structure is
caused by the `loop()` / `delay(1)` receive-handling cadence, that interval
should co-vary with RTT.

## Host runner

Pure parser/derivation self-test:

```powershell
py hardware/lilygo-lora32-v1.6.1/host/hw002_timing.py selftest
```

One physical timing measurement:

```powershell
py hardware/lilygo-lora32-v1.6.1/host/hw002_timing.py measure `
  --initiator-port COM3 `
  --responder-port COM4 `
  --seq 1 `
  --bytes 42 `
  --timeout-ms 3000
```

A paced timing benchmark is dry-run by default. RF execution still requires an
explicit airtime budget and TX-occupancy pacing input:

```powershell
py hardware/lilygo-lora32-v1.6.1/host/hw002_timing.py benchmark `
  --initiator-port COM3 `
  --responder-port COM4 `
  --bytes 42 `
  --count 20 `
  --timeout-ms 3000 `
  --execute `
  --airtime-budget-ms 2000 `
  --tx-occupancy-cap-percent 1.0 `
  --environment "same-bench-indoor-timing" `
  --output hardware/lilygo-lora32-v1.6.1/physical-validation/hw002t-com3-42b-20.json
```

The occupancy input remains an experiment pacing parameter, not a claim of
regulatory compliance.

## Physical workflow

HW-002T changes firmware instrumentation, so the already collected HW-002
baseline remains frozen and is not silently reinterpreted.

For the first HW-002T physical checkpoint:

1. sync the repository;
2. flash the same HW-002T firmware on both boards, antennas attached before any
   RF test;
3. verify `READY hw-002t` and `timing_trace=1`;
4. run `hw002_timing.py selftest`;
5. run one 42-byte dual-port measurement;
6. only if the trace is internally consistent, run a paced 20×42-byte series in
   each initiator direction;
7. compare RTT with `irq_to_handle_us` and the other responder-local phases.

Only after this timing checkpoint should the experiment move to distance/NLOS
sweeps.

## Scientific boundary

HW-002T is instrumentation, not a new network protocol. It does not establish a
causal explanation until physical traces show where the RTT variation occurs.
Do not infer one-way latency or propagation distance from the cross-board
residual.
