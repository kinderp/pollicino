# HW-002 — physical LoRa measurement ping/pong

HW-002 turns the successful HW-001 link into a repeatable measurement instrument.
It keeps the same two LILYGO LoRa32 V1.6.1 / SX1276 boards and the same frozen
bench PHY:

- 868.100 MHz;
- 125 kHz bandwidth;
- SF7;
- coding rate 4/5;
- private sync word `0x12`;
- 10 dBm TX power;
- 8-symbol preamble.

The first objective is deliberately narrow: **measure the direct bare-LoRa
link before changing radio parameters**.

## Why a firmware ping/pong?

HW-001 measured one-way receive RSSI/SNR while Python orchestrated both serial
ports. That was enough to prove exact transport.

For latency measurements, however, a PC-mediated exchange would include:

```text
radio + USB + Windows scheduling + Python + USB + radio
```

HW-002 therefore moves PING/PONG into the two radios:

```text
PC
 |
 | MPING
 v
Board A
 |                              Board B
 |------ H2 PING / LoRa ------->|
 |                              | measure A->B RSSI/SNR
 |<------ H2 PONG / LoRa -------|
 | measure B->A RSSI/SNR
 | compute RTT
 v
PC <- one MRESULT line
```

The PC starts the measurement but is not in the RF turnaround path.

## Measurement frame

`H2` is **hardware instrumentation only**. It is not a PollicinoNet core wire
format and must not be imported by `pollicino.net`.

PING and PONG have the same selected frame length (16..240 bytes). They carry:

- `H2` magic + version;
- PING/PONG type;
- 16-bit sequence;
- CRC16-CCITT over deterministic probe bytes;
- in the PONG, receiver-observed RSSI and SNR;
- deterministic probe bytes echoed unchanged.

The radio also keeps its own LoRa payload CRC enabled. The extra H2 CRC exists
to make the measurement payload itself independently checkable.

## New serial commands

### `TOA <bytes>`

No RF transmission occurs.

Example:

```text
TOA 42
```

Response:

```text
TOA bytes=42 us=<microseconds>
```

The value comes from RadioLib `SX127x::getTimeOnAir()` using the **currently
configured modem parameters**.

### `MPING <sequence> <bytes> <timeout_ms>`

Example:

```text
MPING 1 42 3000
```

Board A transmits one H2 PING. Any HW-002 board that receives a valid H2 PING
automatically returns an equal-sized H2 PONG.

Successful result shape:

```text
MRESULT seq=1 bytes=42 success=1 rtt_us=... tx_block_us=... toa_us=... remote_rssi_dbm=... remote_snr_db=... local_rssi_dbm=... local_snr_db=...
```

Semantics:

- `remote_*`: measured by Board B while receiving A -> B PING;
- `local_*`: measured by Board A while receiving B -> A PONG;
- `rtt_us`: firmware-level RF transaction time, excluding host USB/Python turnaround;
- `tx_block_us`: measured duration of A's blocking transmit call;
- `toa_us`: RadioLib predicted time-on-air for one frame.

Failure shape:

```text
MRESULT seq=1 bytes=42 success=0 error=timeout ...
```

A timeout proves only that a valid PONG was not received by the initiator. It
cannot prove whether B never received the PING, B transmitted a PONG that was
lost, or another link-layer event intervened.

## Host runner

Pure host self-test:

```powershell
py hardware/lilygo-lora32-v1.6.1/host/hw002.py selftest
```

### Plan first — no RF

After flashing HW-002 on both boards, leave the responder powered with its
antenna attached. On the initiator:

```powershell
py hardware/lilygo-lora32-v1.6.1/host/hw002.py plan `
  --port COM3 `
  --sizes 16,32,42,60,120,240 `
  --count 3
```

This asks the firmware for time-on-air and prints the planned per-node TX
budget. It does not transmit LoRa packets.

Optional research pacing calculation:

```powershell
py hardware/lilygo-lora32-v1.6.1/host/hw002.py plan `
  --port COM3 `
  --sizes 16,32,42,60,120,240 `
  --count 3 `
  --tx-occupancy-cap-percent 1
```

`tx-occupancy-cap-percent` is an **experiment pacing input**, not a statement
that a given percentage is legally permitted in the current region/sub-band.
Always verify current rules before RF execution.

### One physical measurement

```powershell
py hardware/lilygo-lora32-v1.6.1/host/hw002.py measure `
  --port COM3 `
  --seq 1 `
  --bytes 42 `
  --timeout-ms 3000
```

Only the initiator serial port is opened. The second board answers entirely in
firmware.

### Batch benchmark

`benchmark` is dry-run by default:

```powershell
py hardware/lilygo-lora32-v1.6.1/host/hw002.py benchmark `
  --port COM3 `
  --sizes 16,32,42,60,120,240 `
  --count 3
```

To actually transmit, two explicit safeguards are required:

1. a per-node planned airtime budget;
2. a requested TX-occupancy pacing cap.

Example **syntax only** (choose values after checking current local RF rules):

```powershell
py hardware/lilygo-lora32-v1.6.1/host/hw002.py benchmark `
  --port COM3 `
  --sizes 16,32,42,60 `
  --count 3 `
  --execute `
  --airtime-budget-ms 2000 `
  --tx-occupancy-cap-percent 1 `
  --distance-m 2 `
  --environment "indoor same room" `
  --output hardware/lilygo-lora32-v1.6.1/physical-validation/hw002-room.json
```

The program refuses to execute if planned per-node TX airtime exceeds the
explicit budget.

## Output metrics

For each successful transaction:

- sequence;
- frame bytes;
- RTT;
- predicted time-on-air;
- measured blocking TX duration;
- A -> B RSSI/SNR;
- B -> A RSSI/SNR.

Aggregates include:

- attempts/success/failures;
- success/loss rate;
- RTT min/mean/p50/p95/max;
- RSSI/SNR statistics in both directions;
- initiator radio bytes and airtime;
- confirmed responder radio bytes and airtime lower bound.

Why a lower bound? If a transaction fails, B may have transmitted a PONG that
was lost. A cannot know that from its own observation alone.

## Experimental sequence

Keep the radio profile fixed first.

Suggested checkpoints:

1. same desk / known short distance;
2. same room;
3. different room;
4. different floor;
5. controlled outdoor line-of-sight tests only after reviewing current local
   spectrum rules and choosing an appropriate protocol.

At each checkpoint record distance/environment and use the same sizes/counts.
Only after this baseline should HW-003 vary SF/BW/CR/power.

## Relationship to FreakWAN

The measurement PING/PONG idea is intentionally comparable with FreakWAN's
connectivity ping, which reports RTT and bidirectional signal strength. We do
**not** copy FreakWAN's packet format or make PollicinoNet depend on MicroPython.

FreakWAN remains a reference/baseline; the validated Pollicino hardware adapter
continues to use RadioLib.

## Regulatory boundary

HW-002 is a research tool, not a compliance engine. Frequency, power, duty/
occupancy and deployment rules depend on region, sub-band, equipment and use.
The host runner therefore records/paces airtime but does not hard-code a claim
that a particular percentage is legal.
