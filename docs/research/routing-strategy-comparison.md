# Synthetic routing strategy comparison

PollicinoNet can now run the **same initial synthetic network state** independently under different routing policies and compare the resulting behavior without treating a policy heuristic as physical evidence.

## Why this exists

A relay network has competing goals:

- deliver as many bundles as possible;
- deliver urgent bundles quickly;
- avoid wasting scarce-link bytes;
- avoid useless replication;
- remain robust when topology hints are wrong;
- defer large data to richer bearers when appropriate.

There is no single strategy that is automatically best on all of those axes. The comparator therefore reports observable metrics instead of embedding a hidden global score.

## Built-in strategies

### `FloodAllStrategy`

Every contact may carry every transferable bundle.

Simple interpretation: **"give useful data to anyone I meet."**

Expected trade-off:

- robust to missing/wrong topology knowledge;
- potentially high duplicate/wire cost.

### `GatewayProgressStrategy`

A synthetic peer rank is supplied. Lower rank means "closer to the gateway" in the scenario model. A window is used only when the target rank is lower than the source rank.

Simple interpretation: **"forward only if the next node looks closer to the destination."**

The rank is scenario metadata. It is not RSSI, geographic distance or a measured probability of delivery.

### `EmergencyFloodProgressStrategy`

- `EMERGENCY` bundles may be flooded even when a contact does not improve the synthetic gateway rank;
- lower-priority bundles still require gateway progress.

Simple interpretation: **"be conservative for ordinary traffic, but replicate emergencies more aggressively."**

This explicitly lets us study the cost/robustness trade-off of emergency redundancy.

### `HoldLargeOnBearerStrategy`

Large non-urgent objects can be withheld from selected bearer kinds (initially useful for experiments such as LoRa) while remaining eligible on richer bearers such as Wi-Fi.

Simple interpretation: **"do not spend scarce bearer budget on a large normal file if a richer contact may appear later."**

The size threshold is local policy. It is not a measured LoRa capacity limit.

## Fair comparison

Each strategy receives an independent clone of:

- peer content state;
- custody ledger;
- fair-scheduler state;
- the same bundle set;
- the same synthetic contact windows;
- the same bearer profiles and logical budgets.

A strategy therefore cannot benefit from traffic generated by another strategy. The input network passed to the comparator is not mutated.

## Reported metrics

For each strategy the report includes:

- delivered bundle count;
- delivered `EMERGENCY` bundle count;
- bundles expired before delivery by scenario end;
- first synthetic delivery time per bundle;
- logical source bytes used;
- total modeled wire bytes;
- skipped windows;
- per-bearer logical/wire usage;
- which bundles each strategy excluded in each contact window.

These metrics expose trade-offs. For example, a progress-only policy may use fewer bytes than flooding but lose an emergency when its topology hint is wrong. Conversely, emergency flooding may restore delivery by spending more wire bytes.

## Validated scenarios

The targeted tests include:

1. **Flood vs gateway progress** — both reach the destination, but progress avoids an unhelpful contact and uses less wire traffic.
2. **Wrong progress hint** — gateway progress misses an emergency route, while emergency flooding replicates across the apparently worse contact and later reaches the destination.
3. **Large normal object** — flooding sends it immediately over synthetic LoRa; hold-large policy waits for a later synthetic Wi-Fi window, reducing LoRa payload at the cost of later delivery.
4. **State isolation** — comparison runs do not mutate the original input network.

## Scientific boundary

This module compares **routing policy behavior under synthetic scenarios**.

It does not establish:

- LoRa range;
- contact probability;
- bytes transferable in a real time window;
- real mobility patterns;
- a deployment-optimal routing policy.

Synthetic peer ranks, window durations and logical source-byte budgets remain scenario inputs. Even a bearer profile whose parameters came from measurements does not make a synthetic comparison a new physical experiment.

## Hardware gate

HW-006 becomes necessary before routing decisions use measured LoRa contact opportunity/capacity or before we claim that a policy is better for the real student network. The physical campaign must first establish the transition region and then measure actual control/data frame behavior so contact-window capacity can be calibrated from evidence.

Until then, routing comparison is valuable for software correctness, policy design, failure-mode discovery and preparing the future distributed student testbed.
